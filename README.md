# 法律法规库 · 党内法规与国家法律法规一体化检索平台

一个**完全离线、单机可用**的中文法规库网页应用。四个数据源：

* **党内法规**：党章、准则、条例、规定、办法、规则、细则、配套规范性文件、组工文件与党务知识
  ——取自人民网党建频道「党章党规」书架 **与** 共产党员网「党章党规」专页
  （`www.12371.cn/special/dnfg/`，两源互补，重合部分按「同一部法规取现行版」去重）。
* **国家法律法规**：宪法、法律、行政法规、监察法规 ——取自**国家法律法规数据库**
  （`flk.npc.gov.cn`），**按需求已排除地方法规与司法解释**。
* **湖北地方法规**：湖北省本级与 13 个市州的地方性法规、法规性决定，以及恩施州、五峰县、
  长阳县的自治条例与单行条例 ——取自**湖北法规库**（`119.36.213.154:8088/fgk/`）。

合计 **2,706 部**法规、约 **1,348 万字**，支持全文检索、分类浏览、收藏夹、自建条目与多格式导出；
数据随页面内置，**双击 `index.html` 即可离线使用**。

> 目标浏览器：**Chrome 69**（2018 年版）——代码与样式已按该版本特性约束编写，不使用 flex `gap`、
> `clamp()`、`:is()`、`aspect-ratio`、`backdrop-filter` 等新特性，也不使用可选链 `?.`、空值合并 `??`、
> `replaceAll`、`Object.fromEntries` 等新语法。

## 一、快速开始

### 方式 A：双击打开（最简单）

双击 `index.html` 即可。数据已随页面内置，**无需联网、无需安装任何服务**。

* 收藏、自建条目、偏好设置保存在浏览器 localStorage（`file://` 协议下同样可用）。
* 如需把本工具固定到 Chrome：打开 `index.html` → 菜单 →「投放更多」/「创建快捷方式」。

### 方式 B：本地服务器（推荐，行为与线上一致）

双击 `启动.cmd`，脚本会在本机 `8765` 端口启动静态服务器并自动打开 Chrome：

```
http://127.0.0.1:8765/index.html
```

也可以手动执行：

```powershell
python -m http.server 8765 --bind 127.0.0.1
```

```

├── 启动.cmd                       Windows 一键启动（本地服务器 + 打开浏览器）

│   ├── css/style.css              设计系统（配色、组件、响应式、打印样式）
│   ├── img/                       本地图片素材（横幅底图、国徽、大会堂剪影、华表）
│   └── js/
│       ├── store.js               本地存储：收藏 / 自建条目 / 设置 / 最近浏览 / 划线批注
│       ├── search.js              检索引擎：解析、加权评分、片段摘要、高亮
│       ├── exporter.js            导出器：Markdown / TXT / HTML / JSON / CSV / 打印
│       ├── markdown.js            轻量 Markdown 渲染器（无依赖，兼容 Chrome 69）
│       └── app.js                 应用主体：路由、视图渲染、阅读设置、划线批注
├── data/
│   ├── regulations.js             **启动必载**（约 2.2MB）：全库 2,706 条的元信息 + 门类 + 分组
│   │                               （window.FG_DATA，含 bodyFiles 分片清单与每条的 bf 标记）
│   ├── regulations.json           同一份元信息的 JSON 版，便于二次开发
│   ├── party_01.js … party_07.js  党内法规正文分片（window.FG_PARTY，共 7 片）
│   ├── flk_01.js … flk_12.js      国家法律法规正文分片（window.FG_FLK，共 12 片）
│   └── hubei_01.js … hubei_05.js  湖北地方法规正文分片（window.FG_HUBEI，共 5 片）
├── tools/                         数据抓取、构建与验证脚本（Python + Node）
└── README.md
```

> **为什么正文要拆出去**：正文总量约 39MB（1,347 万字），全部在启动时当 JS 对象字面量解析，
> 低配机器上光解析就要好几秒，页面长时间白屏。现在启动只解析 2.2MB 的元信息，
> 正文**按需加载**：打开详情页只加载那一条所在的那一个分片，检索才加载全部分片。
> 分片由 `assets/js/app.js` 用 `<script>` 动态引入（`file://` 下同样可用），
> 每加载到一片就立刻把正文并回记录并**增量重建索引**，不必等 24 片全部下完才出结果。

> **为什么分片**：正文总量远大于元信息，单个 JS 文件会超过 10 MB，影响 `file://` 下的首屏解析。
> 现在按**字数**切（每片约 60 万字 ≈ 1.8MB），共 24 片（党内 7 / 国家库 12 / 湖北 5），
> 单片最大 1.9MB，可以只加载需要的那一片。

> **Word 预览已下线**（2026-10）：详情页只保留 Markdown 一种正文形式。
> 原先由 `.docx` 转出的预览分片（`data/word_NN.js`，约 29.6 MB）已删除，
> `tools/word_html.py` 保留但不再参与构建；原始 `.docx` 原件仍在
> `tools/flk_cache/` 与 `tools/hubei_cache/`，需要时可随时恢复。

### 重复条目清理

原始抓取数据里存在三类「重复条目」，构建期统一清理（规则写在 `tools/build_dataset.py`，
数据可复现，不靠手工删文件）：

| 类型 | 判定依据 | 处理 |
| --- | --- | --- |
| **同一部法规的多个历史版本** | flk 的「修订沿革」链（`lsyg`）把历次版本连成一簇 | 每簇只保留**现行有效 / 尚未生效**的版本；整簇都失效时只留公布日期最新的一条。删 199 条 |
| **旧版与现行版标题相同、但没建沿革关系** | 标题相同 + 时效性（已废止/已修改 vs 有效）+ 正文相似度 ≥ 0.5 | 删已被取代的旧版；正文逐字相同的只留一条。共再删 90 条 |
| **党内法规内部重复** | 人民网「党章党规」书架与「组工文件／党务知识」栏目收录同一篇 | 保留党内法规门类下那一份，删另一份。删 40 条 |
| **人民网 × 共产党员网 重复** | 标题归一后相同（剥离「（2025年11月28日发布）」这类日期后缀）+ 正文相似度 ≥ 0.6 | 同一部法规只留一条：**公布日期准确的那份优先**（正文里有发文日期行的胜出），日期新的优先，再按门类层级与正文长度 |
| **跨源重复** | 标题相同且正文与国家库那份相似度 ≥ 0.8 | **以国家法律法规库为准**，删党内那份。删 3 条 |

* **历史版本的信息不会丢**：保留条目的「修订沿革」面板仍列出历次版本的标题与公布日期。
* **同名但不同的文件全部保留**：如历年《国务院关于修改和废止部分行政法规的决定》、
  《全国人民代表大会常务委员会组成人员守则》，它们是各自独立的法规，不能按标题归并。
  这类条目在标题后补版本后缀（如「（2026-08-28 修订，2027-01-01 施行）」）以便一眼区分。
* **湖北库内部无重复**（509 条标题互不相同），与国家库也无正文重复；
  「湖北省实施《××法》办法」与《××法》本身是包含关系而非重复，两边都留。

> **注意**：国家法律法规下载接口带创宇盾（WZWS）风控，直接用脚本请求会被 JS 挑战拦截，
> 因此正文附件改由真实 Chrome 驱动下载（`tools/crawl_flk_ctx.js`，通过 CDP 控制）。
> 下载时每个 worker 使用**独立浏览器上下文**隔离下载目录——否则多个并发 worker 会互相覆盖
> `downloadPath`，把 A 篇的文件记到 B 篇名下。落盘前还会用文件名里的标题反查一次，
> `tools/verify_flk_mapping.py` 可随时全量体检。
> 风控收紧到「图形验证码」时须停止请求、冷却十几分钟后再继续，并把下载间隔拉大。

> **flk 的历史版本附件会「串档」**：下载某些历史版本（`bbbs` 以 `ff808081`/`ff808181`/`2c909fdd`
> 开头）时，服务端可能返回**另一部法规**的 docx——文件名是对的，内容却是别人的。
> 本轮体检发现 9 条，已用 `tools/make_fix_items.py` + `crawl_flk_ctx.js` 重新下载修复 8 条；
> 剩下 1 条（全国人大常委会关于《香港基本法》第二十二条第四款和第二十四条第二款第（三）项的解释）
> 服务端始终不返回正确附件，已从缓存移除，避免挂着他法正文充数。
> 检测方法见 `tools/wrong_owner.py`（按正文指纹找「不同标题却同一篇正文」的组，
> 再用 docx 标题区判定哪条才是真正的主人）。

> **源文档里的「目 录」不是正文**：flk 导出的 docx 开头常带一段目录（「第八章 其他规定」
> 「分 则」等），早期解析器把它当成正文切分点，于是目录里出现「正文根本没有的章」。
> 现在由 `tools/section_parser.py` 统一处理：目录条目按「同名标题在正文里还会再出现」判定并剥离，
> 章节层级按「第X章＝一级、第X节＝二级」标注。改动解析逻辑后必须重跑
> `python tools\repair_flk_sections.py`，再 `build_dataset.py`。

> **docx 要按 OOXML 结构解析**：flk 导出的 docx 是美化过的 XML，标签之间带 CRLF 缩进。
> 用「正则剥标签 + 按 `\n` 切行」的话，每个 run 边界都会残留换行——条文里「第一条」是黑体 run、
> 正文是仿宋 run，于是两者被拆成两行，Markdown 视图里条号就单独成段了。
> 现在段落边界只认 `<w:p>`、段内换行只认 `<w:br/>`，解析集中在 `tools/section_parser.py`。

> **湖北条例的章节标题会折行**：「第一节 人民代表大会及其常务委员会有关人员」在源文档里
> 会被排版成两行（下一行是「的任免」）。不合并的话，标题被截断、后半截变成正文，
> 目录里的条目名也跟正文对不上（目录块剥离随之失效）。
> `section_parser.merge_heading_continuations()` 负责把短续行并回标题。

### 日期口径

三个数据源的日期语义已统一，避免「时间轴分组年份 ≠ 卡片显示年份」这类错位：

| 字段 | 含义 | 取值来源 |
| --- | --- | --- |
| `published` | **现行版本公布日** | flk：`gbrq`（公布日期）→ 修订日 → 通过日；湖北：详情页「公布日期」；党内：摘要里最后一个「发布/印发/公布/颁布」或「修订/修正/修改」事件日，无事件词时退回修订日→通过日 |
| `adopted` | 初版通过日 | 各源原始字段 |
| `revised` | 最后修订日 | 各源原始字段 |
| `effective` | 施行日期 | 各源原始字段 |

* `year` 统一由 `published` 推导，全库 0 条年份与公布日期不一致。
* 时间轴按 `published` 分组，卡片显示的也是 `published`。
* **共产党员网的「新闻通稿」体例文件**（正文里根本没有发文日期，如「中共中央印发《意见》的通知」）
  用**网页发布时间**兜底 —— 该日期取自文章 URL 里的 `/2023/04/18/`。
  这类条目的 `published` 精度只到「网页发布日」，详情页的「数据来源」会标明是共产党员网。
* 有 **146 部**法规源数据本身没有任何日期（党务知识 111、规范性文件与办法等若干），
  记为 `published = "年份"` 或留空，不编造日期，因此它们不进时间轴。

视觉基调取自**国家法律法规数据库（flk.npc.gov.cn）官网首页**：红金横幅 + 国徽 + 人民大会堂柱廊。
素材已下载到 `assets/img/` 随站点打包，**不产生任何外部请求**，`file://` 双击打开也能正常显示。

* **首页**：红金通栏 Hero（国徽 + 站名 + 副标题 + 超大检索框 + 热门词）→ 7 个门类卡片**半透明浮压在横幅下缘**（身后透出大会堂柱影）→ 4 个统计卡（总数／正文字数／门类数／数据版本）→ 新法速递／全库门类双栏面板 → 页脚（人民大会堂剪影 + 内容来源说明）。

  搜索框**撑满**中间空间（不设固定宽度），右侧是主题切换与「新增条目」，**顶栏右缘与正文区右缘严格对齐**——
  早先搜索框卡在 720px 宽、按钮组紧贴其右，顶栏内容全挤在左边 1170px，右边空出一大片，很不协调。
* **侧栏**：只做**范围导航**，不做功能菜单——检索组 3 个 + 我的组 3 个，下面是可折叠的**法规体系树**
  （国家法律法规／党内法规／党务资料／本机数据／湖北地方法规 → 17 个门类）。
  默认全部折叠，进入某门类时自动展开它所在的体系，当前门类与当前体系同时高亮。
* **按钮系统**：三级（primary / ghost / danger）+ 固定高度 36 / 30 / 26px；
  图标一律用统一的**内联线性 SVG**（`assets/js/app.js` 的 `ICON` 常量），
  字符图标（★☆◆◷⌕）与 emoji 全部淘汰。
* **配色**：底色是暖调纸面 `#f5f4f0`（比纯白柔和，长时间阅读不刺眼），分隔线 `#e5e2d9` 同为暖调；章标题引导线取国徽金。

  正文**用宋体**（法规原文惯例，中文小字长文更耐读），标题与元信息用黑体；17px 字号 / 行距 2.02，约 39 汉字/行。
  窄屏（≤1200px）目录自动移到正文下方。
* **阅读主题**：6 套背景只作用在正文区（`.doc-layout`），不牵连站点其它部分；
  主题变量挂在 `.doc-layout` 上并**显式写一次 `color: var(--ink)`**——

  阅读主题（羊皮／夜间等）在打印时同样强制切回白底，划线改用下划线表示（浏览器默认不打印背景色）。

### 阅读功能：划线、批注与「我的笔记」

划线批注存在浏览器本地（localStorage 的 `fg.marks.v1`），与收藏、自建条目一样**不上传任何服务器**，
导出完整备份时会一并带出。

* **锚点**：一条划线记的是「正文纯文本的字符偏移（s/e）+ 选中原文（t）」。
  法规数据更新后偏移会漂移，渲染时先用偏移校验，对不上就**按原文回退定位**；
  两者都对不上才丢弃这条划线，并提示「有 N 条划线因法规更新未能复原」。
* **铺回正文**：Chrome 69 没有 `CSS.highlights`（Chrome 105+），改用 `splitText` 手工包 `<mark class="fg-hl">`。
  每次铺之前先把已有的 `<mark>` 拆回纯文本再重铺，否则「新增一条后重铺全部」会在旧划线里再套一层。
* **作用域**：阅读设置有「全局默认」与「单篇单独设置」两层。勾上「本篇单独设置」后，
  改的是 `settings.readPerDoc[docId]`；不勾则改全局。两者互不干扰，自检里有对应断言。
* **与检索高亮区分**：检索高亮用的是裸 `<mark>`（红色底 + 加粗），
  划线用 `<mark class="fg-hl">`。深色站点下裸 `<mark>` 的文字会被染成浅粉色，
  所以划线用 `mark.fg-hl` 更高优先级的选择器把颜色、字重、底色都拿回来。

### 低配机器上的性能取舍

在配置较低的机器（老笔记本、2GB 内存的小主机、无 GPU 的虚拟机）上用 Chrome 打开时，
最初版本是「打开就卡、滚动就顿」。实测定位到的三处瓶颈与对应做法：

| 瓶颈 | 原来 | 现在 |
| --- | --- | --- |
| **启动解析** | 52MB 正文当 JS 对象字面量一次性解析，白屏好几秒 | 启动只解析 **2.2MB 元信息**；正文 39MB 拆成 **24 个分片**（每片约 60 万字 ≈ 1.8MB），**打开详情页只加载那一片**，检索才加载全部分片并显示进度；每加载到一片就**立刻增量建索引**，不必等全部下完 |
| **DOM 规模** | 时间轴一次渲染 2,706 张卡片 = **13,043 个 DOM 节点**；体系页 5,241 个；门类页 2,838 个 | 分批渲染：时间轴先出一批（≤200 张卡片），体系/门类页先出 120 条，底部「再显示」按需追加（只往尾部插，不重绘） |
| **动画与输入** | 每次切页给 `.view` 下**每个**子元素做入场动画（时间轴一次 60 多个合成层）；搜索框每敲一个键都全量扫库做联想 | 动画只作用于前 6 个子元素；联想输入**防抖 150ms** |

实测（本机 Chrome，窗口 1440×1050）：

* 启动：`domInteractive` **284ms → 137ms**，JS 堆 **105MB → 6MB**
* 时间轴 DOM：13,043 → **1,040** 个节点；体系页 5,241 → **499**；门类页 2,838 → **496**
* 检索命中数、导出内容、全库条目数均未变（自检 **169 项**全绿）

> 正文按需加载只影响**首次**打开详情页/检索的等待（之后浏览器会缓存这些分片）；
> 若只浏览首页、门类、时间轴，全程不再需要加载正文。
